How judging works

Platforms say they normalize scores. This one shows you exactly how, and lets organizers compare methods before they publish.

{{ ui.shead("01", "Scorecards") }}

Each judge scores each assigned project on every rubric criterion (1–5 by default). The organizer sets a weight per criterion, optionally per track. A scorecard's weighted total is

weighted = Σ weight(c) · score(c) / Σ weight(c)

Weights apply when results are computed, so re-weighting never rewrites a stored score, and every change is in the audit log.

{{ ui.shead("02", "Why normalize") }}

Judges differ. Some give everything a 4; some never give a 5. With 3–5 judges per project, the luck of the draw can move a project several places. Normalization removes each judge's personal offset so projects are compared on their merits.

{{ ui.shead("03", "The default: judge-bias model") }}

We fit an additive model to every scorecard: score = overall mean + project quality + judge bias + noise, by least squares with a ridge penalty (λ = 2) on the judge biases.

  • Judges who reviewed overlapping projects are compared on that shared work, so a judge who was simply handed a strong batch is not mistaken for a generous one.
  • A judge with few reviews gets a bias estimate shrunk toward zero: no evidence, no correction.
  • The published score is mean + project quality, still on the rubric scale.

Organizers can also view, and choose, a shrunk per-judge z-score, the raw mean, or a within-judge Bradley–Terry ranking that uses only the order of each judge's scores. The organizer's results page shows every project's rank under all four, with movements relative to the raw mean.

{{ ui.shead("04", "Isolation") }}
  • Judges see only projects in their tracks, and only their own scores. Requests for anything else get 403 from the server.
  • Nobody but organizers sees aggregate scores before results are published.
  • Every organizer action that affects results is written to a hash-chained audit log.
